# 软件设计 · 从需求基线到 PM Agent

用户可以从自己的软件想法开始，例如开发一个新工具、给现有系统增加功能，或改善已有模块的性能。HAMA-Loop 在 live 模式下围绕本次输入澄清需求并发布经确认的 PRD。拟建的软件设计阶段根据这份 PRD 和目标工程生成专属 Design Spec，经人确认后，交由现有 PM Agent 分解任务，再进入编码与验证。校园活动报名仅是一组演示数据。

| 使用场景 | 阅读入口 | 交付内容 |
| --- | --- | --- |
| 设计、实现或答辩本阶段 | [子系统设计说明](./subsystem-design.md) | 系统边界、技术选型、模块、数据与接口契约、设计版本和评审流程 |
| 为自己的需求撰写设计 | [通用 Design Spec 模板](./design-spec-template.md) | 从本项目 PRD 提取设计输入、填写评审稿并生成 PM 导入正文 |
| 实现通用设计流程 | [实现与验收方案](./implementation-plan.md) | 输入契约、设计推导、代码接入点、分期交付与跨项目验证 |
| 查看一个已填写的案例 | [校园活动报名设计评审稿](./campus-design-review.md) | 需求来源、技术决策、接口行为、事务、追踪矩阵和待确认项 |
| 在编排器中演练拆解 | [校园活动报名 Design Spec](./campus-design-spec.md) | 与评审稿配套的 PM 输入，含模块文件范围、FR、AC 和交付约束 |

## 当前可用方式

1. 在「需求工程」页确认 PRD，读取已发布的基线。保留其项目 ID、基线 ID、版本、SHA-256 与原始需求和验收编号。校园演示可用于文档演练，正式交接使用 live 基线。
2. 使用通用模板，根据当前基线的每条需求、验收条件及目标工程填写评审稿。已有项目引用现有入口和代码，新项目声明拟新增的入口与文件。记录技术假设和待确认项；涉及用户目标或验收口径的变化交回需求工程。
3. 评审人逐项核对追踪矩阵、接口失败路径和数据不变量，记录意见及处理结果。设计负责人和确认人保存所审文档版本及摘要。当前可人工执行，拟建的自动生成、版本管理和确认服务见子系统设计说明。
4. 如需演练 PM 拆解，在工作流导入面板载入 Design Spec 的 Markdown 文件。当前页面取工作区列表第一项作为目标，使用前核对目标工作区；需要显式指定时，可通过现有导入 API 传入 workspaceId。检查 PM 报告中的模块、需求引用和文件范围，核对后再决定试运行与锁版。校园案例的目标应用代码和业务测试需要另行实现。

**交接边界。** 现有「导入下游编排」会从真实基线直接生成工作流。手工导入 Design Spec 则创建独立的工作流，适合验证文档与 PM 的适配性。两次导入会产生两个 workflowId。正式实现应采用设计说明中的一次结构化交接，同时携带基线和设计信息。
