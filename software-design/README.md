# 软件设计 · 从需求基线到 PM Agent

本模块负责把用户项目已确认的 **PRD 转换为 Design Spec，并将确认版传入仓库已实现的 PM Agent**。HAMA 提供 PRD 及其基线，软件设计阶段补齐架构、模块、接口、数据规则、文件范围和验收映射。交接完成的依据是现有 Planner 返回本次设计对应的 GoalSpec 与 PM 报告。任务分解、编码执行和业务验收由下游负责。校园活动报名仅为演示案例。

| 使用场景 | 阅读入口 | 交付内容 |
| --- | --- | --- |
| 设计、实现或答辩本阶段 | [子系统设计说明](./subsystem-design.md) | 系统边界、技术选型、模块、数据与接口契约、设计版本和评审流程 |
| 为自己的需求撰写设计 | [通用 Design Spec 模板](./design-spec-template.md) | 从本项目 PRD 提取设计输入、填写评审稿并生成 PM 导入正文 |
| 实现通用设计流程 | [实现与验收方案](./implementation-plan.md) | 输入契约、设计推导、代码接入点、分期交付与跨项目验证 |
| 逐项实施并联调上下游 | [实施与交接清单](./checkoutlist.md) | 从接收 PRD 到现有 PM Agent 签收的六个步骤与证据记录 |
| 查看一个已填写的案例 | [校园活动报名设计评审稿](./campus-design-review.md) | 需求来源、技术决策、接口行为、事务、追踪矩阵和待确认项 |
| 在编排器中演练拆解 | [校园活动报名 Design Spec](./campus-design-spec.md) | 与评审稿配套的 PM 输入，含模块文件范围、FR、AC 和交付约束 |

## 当前可用方式

清单步骤 1–4 已接通：在需求工程页的已发布基线下点击「生成软件设计」，显式选择目标工程并核对提交后保存输入草案，再选择提供商和模型生成正文。页面显示结构化草案、逐项诊断、评审稿及 PM Markdown 预览，支持反馈重试与导出。将成功生成结果保存为评审修订后，可提交评审、逐项退回、追加修订并确认冻结；确认后可查看和导出保留原始编号的结构化 PM 输入。设计及历史决定存入宿主 SQLite，可在重启后重新打开；无提交工程先绑定初始提交，demo 基线仅供演练。实现范围、接口、测试与样例见[步骤 1](./verify/step1-verification.md)、[步骤 2](./verify/step2-verification.md)、[步骤 3](./verify/step3-verification.md)和[步骤 4 验证记录](./verify/step4-verification.md)。正式交接和工作流创建将在步骤 5 实现。

1. 在「需求工程」页确认 PRD，读取已发布的基线。保留其项目 ID、基线 ID、版本、SHA-256 与原始需求和验收编号。校园演示可用于文档演练，正式交接使用 live 基线。
2. 选择模型起草设计正文，或使用通用模板人工填写评审稿。已有项目引用现有入口和代码，新项目声明拟新增的入口与文件。核对诊断、技术假设和待确认项，填写反馈后可重新起草；涉及用户目标或验收口径的变化交回需求工程。
3. 在评审面板填写操作人和逐项意见，提交评审、确认或退回。技术问题在原基线下新增修订并填写处理结果；需求目标或验收标准变化时返回 HAMA，新基线设计可选择旧设计来源并比较原始需求与 AC。确认事务核对修订、状态与摘要，历史正文及决定不可修改。
4. 确认后点击「查看结构化 PM 输入」核对原始需求 / AC、模块、契约、依赖及设计补充检查，并导出 JSON。此操作不创建工作流。Markdown 短编号预览仍可供手工导入演练；正式路径使用结构化对象，避免重新解析而丢失原始编号和 AC 所属关系。

**交接边界。** 现有「导入下游编排」会从真实基线直接生成工作流。手工导入 Design Spec 则创建独立的工作流，适合验证文档与 PM 的适配性。两次导入会产生两个 workflowId。正式实现应采用设计说明中的一次结构化交接，同时携带基线和设计信息。
